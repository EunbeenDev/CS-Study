### 1. 전략 패턴(Strategy Pattern)이란?
- 알고리즘(행위)을 객체로 캡슐화하여 런타임에 자유롭게 교체할 수 있도록 만든 행동 디자인 패턴
- 동일한 문제를 해결하는 여러 알고리즘을 각각 클래스로 분리하고, Context는 알고리즘의 구체적인 구현을 알 필요 없이 전략 인터페이스에만 의존한다.
- 상속이 아닌 합성(composition) 을 통해 동작을 변경하는 패턴이다.
- “무엇을 할지는 고정하고, 어떻게 할지는 바꿀 수 있게 만든다.”

### 2. 장점
- 알고리즘을 사용하는 코드(Context)와 알고리즘 구현(Strategy)을 분리하여 결합도가 낮다.
- 런타임에 전략 객체를 교체할 수 있어 유연한 확장이 가능하다
- 알고리즘 변경 시 Context 코드를 수정하지 않아 OCP(개방/폐쇄 원칙)을 만족한다.
- 각 전략 클래스가 하나의 책임만 가지므로 SRP(단일 책임 원칙) 을 따른다.
- 테스트 시 전략을 독립적으로 검증할 수 있어 테스트 용이성이 높다

### 3. 전략 패턴의 구성 요소
구분 기준은 “알고리즘을 누가 소유하고, 누가 선택하는가?” 이다.
- Strategy (전략 인터페이스): 공통 알고리즘 인터페이스
- ConcreteStrategy (구체 전략): 실제 알고리즘 구현체
- Context (전략을 사용하는 객체): Strategy를 주입받아 사용

### 4. 예시
#### 0) 구조
```scss
   Context
   └─ strategy: Strategy
   ↑
   │
   ┌───────────────┐
   │               │
   ConcreteStrategyA  ConcreteStrategyB
   │               │
   └────── Strategy ────────┘
```
#### 1) Strategy — 전략 인터페이스
- 알고리즘의 공통 인터페이스
```java
// Strategy
public interface PaymentStrategy {
    void pay(int amount);
}
```


#### 2) ConcreteStrategy — 실제 알고리즘 구현
```java
// ConcreteStrategy
public class CardPaymentStrategy implements PaymentStrategy {
    public void pay(int amount) {
        System.out.println(amount + "원을 카드로 결제합니다.");
    }
}
```
```java
public class KakaoPayStrategy implements PaymentStrategy {
    public void pay(int amount) {
        System.out.println(amount + "원을 카카오페이로 결제합니다.");}
}

```

#### 3) Context — 전략을 사용하는 객체
- 구체적인 결제 방식은 모르는 상태로 전략 인터페이스에만 의존
```java
// Context
public class PaymentService {

    private PaymentStrategy strategy;

    // 런타임에 전략 주입
    public PaymentService(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void pay(int amount) {
        strategy.pay(amount);
    }

    // 전략 교체 가능
    public void changeStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }
}
```

4) 클라이언트 사용 예시
```java
public class Client {
   public static void main(String[] args) {
   PaymentService service = new PaymentService(new CardPaymentStrategy());
   service.pay(10000);

        service.changeStrategy(new KakaoPayStrategy());
        service.pay(20000);
   }
}
```

### 5. 언제 사용하면 좋은가?
- 조건문(if / switch)으로 행위 분기가 반복될 때
- 알고리즘 변경 가능성이 높을 때
- 런타임에 동작을 바꿔야 할 때
- Spring에서 다음과 같은 경우에 자주 사용됨
  - 인증 방식(JWT, OAuth, Session)
  - 알림 전송 방식(Email, Push, SMS)

### 참고1) 전략 패턴 vs 템플릿 메소드 패턴
| 구분     | 전략 패턴  | 템플릿 메소드 패턴 |
| ------ | ------ | ---------- |
| 패턴 분류  | 행동 패턴  | 행동 패턴      |
| 핵심 개념  | **합성** | **상속**     |
| 변경 방식  | 객체 교체  | 메소드 오버라이딩  |
| 런타임 변경 | 가능     | 불가능        |
| 유연성    | 높음     | 상대적으로 낮음   |

템플릿 메소드는 알고리즘 구조는 고정하되 일부 단계만 변경하는 패턴이고,
전략 패턴은 알고리즘 전체를 교체하는 패턴이다.

전략 패턴은 “상속(extends)보다 합성(implements)을 선호하라” 원칙을 가장 잘 보여주는 패턴 중 하나이다.

둘 다 OCP를 만족하지만,
팩토리 패턴은 객체 생성의 책임을 분리하고,
전략 패턴은 객체 행위의 책임을 분리한다.
