### 1. 디자인 패턴이란?
상황에 따라 자주 쓰이는 설계 방법을 정리한 방법론으로, 디자인 패턴은 특정 구현 방법이 아닌 아이디어를 말한다.
</br> 구현 방안을 설계할 때 참조할 수 있는 전형적인 해결방식이다.

여러 프로그래밍 문제들을 해결하다 보면 반복적으로 발생하는 고질적인 문제들이 있다.
'바퀴를 다시 발명하지 마라' 라는 격언에서 알 수 있듯이 이미 구현된 것을 다시 만들게 되는 문제가 대표적이다.
이러한 문제들을 해결하는 방법들을 카테고리화하여 패턴별로 정리한 것이 디자인 패턴이다.


<br>

### 2. Gof가 정리한 디자인 패턴의 분류 (3가지)
- 생성 패턴: 객체들을 생성하는 방식이나 생성 시점을 결정하는 패턴
- 구조 패턴: 클래스와 객체를 조합하여 더 큰 구조를 만드는 방법에 대한 패턴
- 행위 패턴: 객체나 클래스 사이의 상호작용과 책임 분배 방법을 정의한 패턴

  | 분류                    | 대표 패턴                                                                                                                           |
  | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
  | **생성 패턴 (Creational)** | Singleton, Factory Method, Abstract Factory, Builder, Prototype                                                                 |
  | **구조 패턴 (Structural)** | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy                                                                 |
  | **행위 패턴 (Behavioral)** | Chain of Responsibility(책임 연쇄 패턴), Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |
<br>

Gof의 디자인 패턴의 종류에는 총 23가지가 있으며, 각 분류 내 패턴 종류에 대한 간략한 설명은 다음과 같다.<br>  
이후 정리에서는 서적 내의 주요 패턴들만 다룰 예정이다.<br>
모든 디자인 패턴들을 외운다기 보다는 어떤 경우에 쓰이면 좋은지에 대해 파악하고 있다가 <br> 필요한 시점에 찾아서 사용할 줄 알면 좋을 것 같다.
#### 1. 생성 패턴
| 패턴                   | 간략 설명                                                                            |
| -------------------- |----------------------------------------------------------------------------------|
| **Singleton**        | 클래스의 인스턴스가 하나만 존재하도록 보장하는 패턴<br/>클래스의 인스턴스를 하나만 생성하고 전역에서 접근 가능하도록 함             |
| **Factory Method**   | 객체 생성 처리 로직을 서브클래스에 분리 및 위임 하여 캡슐화하는 패턴                                          |
| **Abstract Factory** | 관련 있는 객체들을 하나의 팩토리로 묶어 생성하는 패턴<br/>구체적인 클래스에 의존하지 않고 의존적인 객체들의 조합을 만드는 인터페이스를 제공 |
| **Builder**          | 복잡한 객체의 생성 과정을 단계별로 분리하여 생성할 수 있도록 하는 패턴                                         |
| **Prototype**        | 기존 객체를 복사하여 새로운 객체를 생성하는 패턴                                                      |

#### 2. 구조 패턴
| 패턴            | 간략 설명                                                                                                                 |
| ------------- |-----------------------------------------------------------------------------------------------------------------------|
| **Adapter**   | 호환되지 않는 인터페이스를 가진 객체들이 협업할 수 있도록 하는 패턴                                                                                |
| **Bridge**    | 구현과 추상을 분리하여 독립적으로 확장 가능하도록 하는 패턴<br/>클래스 또는 밀접하게 관련된 클래스들의 집합을 두 개의 개별 계층구조(추상화 및 구현)로 나눈 후 각각 독립적으로 개발할 수 있도록 하는 패턴 |
| **Composite** | 객체를 트리 구조로 구성하여 단일 객체처럼 사용하는 패턴                                                                                       |
| **Decorator** | 객체들의 새로운 행동들을 포함한 특수 래퍼 객체들 내에 동적으로 넣어서 위 행동들을 해당 객체들에 연결시키는 패턴                                                       |
| **Facade**    | 복잡한 서브시스템을 단순한 통합된 인터페이스로 제공하는 패턴                                                                                     |
| **Flyweight** | 각 객체에 데이터를 유지하는 대신 여러 객체들의 공통 데이터를 공유하여 RAM에 더 많은 객체를 포함함으로써 메모리 사용을 최소화하는 패턴                                         |
| **Proxy**     | 원본 객체를 대신하여 처리하게 함으로써 원본 객체에 대한 접근과 흐름을 제어하는 패턴                                                                       |

#### 3. 행위 패턴
| 패턴                          | 간략 설명                                                                                                   |
| --------------------------- |---------------------------------------------------------------------------------------------------------|
| **Chain of Responsibility** | 요청을 처리할 수 있는 객체를 체인으로 연결하고, 핸들러의 체인을 따라 요청을 전달하는 패턴<br/> 각 핸들러는 요청을 받으면 처리할 것인지 다음 체인의 핸들러로 전달할지를 결정한다. |
| **Command**                 | 요청을 객체 형태로 캡슐화하는 패턴                                                                                     |
| **Interpreter**             | 언어의 문법을 클래스로 표현하고 특정 언어를 구현하는 패턴                                                                        |
| **Iterator**                | 객체의 기본 표현을 노출하지 않고 원소를 순서대로 순회할 수 있게하는 패턴                                                               |
| **Mediator**                | 객체 간의 직접 통신을 중재자로 분리한 패턴<br/>객체 간의 직접 통신을 제한하고 중재자 객체를 통해서만 통신하게 하므로 객체 간의 혼란스러운 의존 관계들을 줄일 수 있다.       |
| **Memento**                 | 객체의 구현 세부 사항을 공개하지 않으면서 해당 객체의 이전 상태를 저장하고 복원할 수 있게 해주는 패턴                                              |
| **Observer**                | 객체에 상태 변화를 관찰하고, 상태 변화에 따라 관찰하고 있는 객체들이 이를 알 수 있게 만드는 구독 매커니즘의 패턴                                       |
| **State**                   | 객체의 내부 상태가 변경될 때 해당 객체가 그의 행동을 변경할 수 있도록 하는 패턴                                                          |
| **Strategy**                | 알고리즘을 정의하고 캡슐화하여 객체를 상호 교환할 수 있게하는 패턴                                                                                       |
| **Template Method**         | 상위 클래스에서 알고리즘의 골격을 정의하고 구체적인 처리는 서브클래스에 위임해서 처리하는 패턴                                                                          |
| **Visitor**                 | 알고리즘들이 작동하는 객체들로부터 분리할 수 있도록 하는 패턴                                                                                |


디자인 패턴을 고려하며 코드를 짬으로써 기대되는 바는 다음과 같다.
- 효율성
- 가독성
- 호환성
- 높은 재사용성
- 유지보수성

디자인패턴은 라이브러리나 프레임워크를 만드는데 기초적인 원리가 되고 있다.

### 참고1) 프레임워크 vs. 라이브러리 
이 둘의 차이는 구조를 제공하는가?이다.

프레임워크는 전체 어플리케이션의 구조를 정의하여 일정한 개발 패턴을 따르게끔 한다. (제어 흐름을 가지고 있다)

라이브러리는 특정 기능만을 제공할 뿐 어플리케이션의 전체 구조에는 관여하지 않는다. 따라서, 사용하는 개발자 스스로 원하는 방식으로 구조를 설계할 수 있다.
#### 프레임워크
- 원하는 기능 구현에 집중하여 개발할 수 있도록 일정한 형태와 기능을 갖추고 있는 골격, 뼈대
- 예시: Spring Framework,  Django, Flask, Android, Vue.js 등
- 애플리케이션 개발 시 필수적인 코드, 알고리즘, DB연동과 같은 기능을 위해 어느정도 구조(뼈대)를 제공하고, 이러한 구조위에서 사용자가 코드를 작성해서 애플리케이션을 개발하는 형태이다.
- 앱/서버 등의 구동, 메모리 관리, 이벤트 루프 등 공통된 부분은 프레임워크가 관리하고, 사용자는 프레임워크가 정해준 방식대로 클래스, 메소드를 구현하면 된다.

#### 라이브러리
- 단순 활용가능한 도구들의 집합
- 소프트웨어를 개발할 때 컴퓨터 프로그램이 사용하는 비휘발성 자원의 모임
- 미리 작성된 코드, 변수, 함수, 클래스가 라이브러리에 포함된다
- 예시: TensorFlow, Pandas, jQuery 등

### 참고2) Spring 과 Spring Boot
Spring과 Spring Boot는 모두 Spring Framework를 기반으로 한 자바 웹 개발  프레임워크이다.
#### Spring
- 스프링 프레임워크의 핵심 모듈을 모아서 만든 프레임워크
#### Spring Boot
- 스프링 프레임워크를 보다 쉽게 사용할 수 있도록 만든 프레임워크
- 스프링에서 제공하는 기능들을 자동으로 설정하여 개발자가 비즈니스 로직에 집중할 수 있도록 한다.
- 예를 들어 스프링 부트는 스프링 MVC, 스프링 Data JPA, 스프링 Security 등의 기능을 자동으로 설정하여 </br> 개발자가 별도로 설정 파일을 작성하지 않아도 사용할 수 있도록 한다.
는, 스프링 부트 Tomcat이 내장되어 있어 별도의 웹 서버를 설치하지 않아도 된다.

요약하자면,</br>스프링은 개발을 편리하게 도와주는 프레임워크이고,</br>
스프링 부트는 스프링을 편리하게 도와주는 프레임워크이다.
