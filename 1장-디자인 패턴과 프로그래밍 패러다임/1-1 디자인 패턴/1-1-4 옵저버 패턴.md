### 1. 옵저버 패턴(Observer Pattern)이란?
- 객체 간 1:N 의존 관계를 정의하여
- 한 객체(Subject)의 상태가 변경되면, 그 객체에 의존하는 모든 옵저버(Observer)에게 자동으로 변경 사항을 통지하는 행동 디자인 패턴
- 상태를 가진 객체(Subject)와 상태 변화를 감지하는 객체(Observer)를 분리하여 느슨한 결합(loose coupling)을 유지한다
- 이벤트 기반 시스템(Event-driven architecture)의 핵심적인 패턴
- “상태가 바뀌면, 구독자들에게 자동으로 알려준다.”

### 2. 장점
- Subject와 Observer 간의 결합도가 낮다.
- 새로운 Observer를 추가해도 Subject 코드를 수정하지 않아 OCP(개방/폐쇄 원칙)을 만족한다.
- 상태 변경 로직과 후속 처리 로직을 분리하여 SRP(단일 책임 원칙)을 따른다.
- 실시간 알림, 이벤트 처리 구조에 적합하다.
- 변경 전파 로직이 **중앙화**되어 일관성을 유지할 수 있다.

### 3. 옵저버 패턴의 구성 요소
구분 기준은 “누가 상태를 가지고 있고, 누가 이를 감지하는가?” 이다.
- Subject (주제/발행자): 상태를 관리하고 Observer를 등록/제거/알림
- Observer (구독자): Subject의 상태 변화를 통지받는 인터페이스
- ConcreteSubject: 실제 상태를 가지는 객체
- ConcreteObserver: 통지를 받아 실제 동작을 수행하는 객체

### 4. 예시
#### 0) 구조
```scss
   ConcreteSubject
   ├─ attach(Observer)
   ├─ detach(Observer)
   ├─ notifyObservers()
   │
   ▼
   ┌───────────────┐
   │               │
   ObserverA      ObserverB
   │               │
   └────── Observer ────────┘

```

#### 1) Observer — 옵저버 인터페이스
- 상태 변경 시 호출될 메소드를 정의
```java
// Observer
public interface Observer {
    void update(String message);
}
```

#### 2) ConcreteObserver — 실제 구독자
```java
// ConcreteObserver
public class EmailObserver implements Observer {
   public void update(String message) {
       System.out.println("이메일 알림: " + message);
   }
}
```
```java
public class PushObserver implements Observer {
    public void update(String message) {
        System.out.println("푸시 알림: " + message);
    }
}
```

#### 3) Subject — 주제 인터페이스
- Observer 관리 책임
```java
// Subject
public interface Subject {
    void register(Observer observer);
    void unregister(Observer observer);
    void notifyObservers();
}
```

#### 4) ConcreteSubject — 상태를 가진 실제 객체
```java
// ConcreteSubject
import java.util.ArrayList;
import java.util.List;

public class NewsPublisher implements Subject {

    private List<Observer> observers = new ArrayList<>();
    private String news;

    public void publish(String news) {
        this.news = news;
        notifyObservers();
    }

    public void register(Observer observer) {
        observers.add(observer);
    }

    public void unregister(Observer observer) {
        observers.remove(observer);
    }

    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(news);
        }
    }
}
```

##### 5) 클라이언트 사용 예시
```java
public class Client {
   public static void main(String[] args) {
   NewsPublisher publisher = new NewsPublisher();

        Observer email = new EmailObserver();
        Observer push = new PushObserver();

        publisher.register(email);
        publisher.register(push);

        publisher.publish("새로운 뉴스가 등록되었습니다.");
   }
}
```


### 5.언제 사용하면 좋은가?
- 한 객체의 상태 변경이 여러 객체에 영향을 미칠 때
- 알림, 이벤트, 리스너 구조가 필요할 때
- GUI 이벤트 처리
- 도메인 이벤트 처리 (DDD)
- Spring에서 자주 등장하는 경우
    - `ApplicationEventPublisher`
    - `@EventListener`
- 메시지 큐(Kafka, RabbitMQ) 기반 이벤트 처리



### 6. 옵저버 패턴의 단점과 주의점
- Observer가 많아질 경우 알림 전파 비용이 증가할 수 있다.
- 알림 순서가 중요할 경우 제어가 어려워질 수 있다.
- Observer가 제대로 해제되지 않으면 메모리 누수 위험이 있다.
- 디버깅 시 이벤트 흐름이 눈에 잘 보이지 않을 수 있다.
